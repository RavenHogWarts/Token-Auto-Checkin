# 01 · 参考实现分析

对 `reference/api-auto-chekin/` 的逐模块拆解。目标是搞清楚：现有实现**做了什么**、**怎么做的**、**哪些能力可复用**、**哪些是缺口**。

## 1. 技术形态

- **Manifest V3** Chrome 扩展，`background` 为 service worker。
- **纯原生 JavaScript**，无构建步骤、无框架、无 TypeScript。
- 模块通过两种方式加载：
  - service worker 侧：`background.js` 顶部 `importScripts('schedule.js', 'config.js', ...)` 一次性引入所有脚本，全部挂在全局作用域。
  - 工具模块采用 `(function(root){ ... })(self||globalThis)` 的 IIFE 模式，并在结尾 `module.exports`，以便用 `node --test` 跑单元测试。
- **权限**（`manifest.json`）：`cookies`、`storage`、`alarms`、`scripting`、`tabs`、`windows`、`webRequest`，`host_permissions: https://*/*`。

## 3. 核心签到流水线

`executeAllCheckIns` 遍历启用站点，对每个站点：

1. 创建临时后台标签页会话 `createSiteTabSession()`（后台打开、不抢焦点、结束后关闭）。
2. `resolveSiteType`：`type === 'auto'` 时先探测站点类型（URL 提示 → 页面内 `__APP_CONFIG__` / `/api/public/site-info` / `/api/status` 探测），结果写回配置。
3. `maybeUpdateSiteName`：站点名仍是域名时，从页面标题/meta 抓取显示名。
4. 按 `mode` 分流：`visit` → `visitSite()`；否则 `checkInSite()`。
5. 写入 `checkInResults`，更新 badge 进度，`sleep(2000)` 后处理下一个。

`checkInSite()` 按 `type` 分流到 `checkInSub2ApiSite` / `checkInZenApiSite`，或走 NewAPI 主逻辑：

- **认证顺序（统一）**：缓存认证头 → 浏览器已有登录态 → linux.do OAuth。
- 用捕获的头 `doCheckInRequest` 发起签到（优先 service worker `fetch`，需要绕过 Cloudflare 时在标签页内 `fetch`）。
- 失败时的分支处理：
  - **Cloudflare 错误**（403 + `Just a moment` / 返回 HTML）：清缓存、强制刷新登录、标记 `_needsTabExecution` 在标签页内重试。
  - **401**：清缓存、刷新浏览器登录态或 OAuth 后重试。
  - **接口失败但非已签**：`tryOfficialPageFallback` 打开官方页面找按钮点击。
- 可选 `signQueryUrl` 二次核验今日是否已签。

## 4. 页面兜底签到（关键能力）

`checkInFromOfficialPage()` 通过 `chrome.scripting.executeScript` 在页面上下文注入一段脚本，能力包括：

- **劫持 `fetch` / `XMLHttpRequest`**，捕获签到接口的真实响应（匹配 `/checkin`、`/check-in`、`/signin` 等路径）。
- **查找签到按钮**：基于文案正则（`立即签到 / 签到 / Check in now / 领取奖励 / daily check-in` 等）+ 优先级排序 + 可见性/禁用判断。
- **识别已签状态**：文案（`已签到 / Checked in` 等）或禁用按钮。
- **人机验证探测**：文案（`Turnstile / captcha / 安全验证`）+ 选择器（`.cf-turnstile / iframe[src*=challenges.cloudflare.com]` 等）。
- **普通弹窗关闭**：Esc + 关闭类按钮点击（会跳过验证码/登录区域）。
- 点击后轮询捕获响应或已签文案，超时给出候选按钮清单便于诊断。

## 5. 登录 / OAuth 能力

- **NewAPI**：读 `/api/status` 拿 `linuxdo_client_id` + `/api/oauth/state`，打开 `connect.linux.do/oauth2/authorize`，脚本点「允许」，回跳后手动调 `/api/oauth/linuxdo?code=...`，多次轮询 `/api/user/self` 确认 session，再 `webRequest` 捕获认证头 + `chrome.cookies` 兜底 + localStorage token 兜底。
- **Sub2API**：走 `/api/v1/auth/oauth/linuxdo/start?redirect=...`，登录页点「Linux.do 登录」，回跳后从 localStorage（`auth_token/access_token/token`）读 token，读不到就用当前标签页 session 直接在页面内签到。
- **ZenAPI**：走 `/api/u/auth/linuxdo`，回调 URL 带 `linuxdo_token`，写入 localStorage `user_token`，签到请求需 `_needsTabExecution` 在标签页内发。
- **站点登录页通用入口** `startSiteLinuxDoOAuthFromLoginPage`：能自动切换 `/login`、`/sign-in`、`/signin`，勾选「同意协议」复选框，点「Linux.do 登录」，处理新开的 `connect.linux.do` 标签页。

## 6. 人机验证处理

- 每个临时标签页启动 `automationHumanVerificationMonitor`，`setInterval` 轮询注入探测脚本（约 120s 窗口、1s 间隔）。
- 命中验证码/登录页时记录状态；若用户开启「人机验证时前置窗口」开关，则把该标签页/窗口切到前台让用户手动完成。
- 页面脚本检测到验证时通过 `chrome.runtime.sendMessage({action:'humanVerificationDetected'})` 通知后台。
- 结果层面产出 `requiresSecurityCheck`，签到记为失败并给出「需完成人机验证」提示。

## 7. 数据模型（现状）

存储在 `chrome.storage.local`：

- `userSites`：原始站点数组，字段 `{ domain, name, enabled, type, mode, pageUrl }`。
- `buildSiteConfig` 派生出运行期配置：`siteId`（域名点转下划线）、`visitUrl`、`signExecUrl`、`signExecMethod`、`signExecParams`、`signQueryUrl`、`cookieDomain` 等。接口路径按 `type` 硬编码映射。
- `checkInResults`：`{ [siteId]: { status, message, balance?, queryVerified? } }`，`status ∈ success/already/checking/failed/invalid`。
- `authHeadersCache`：`{ [siteId]: { headers, cachedAt } }`，7 天过期。
- `checkInRunState`、`lastCheckInTime`、`autoSignTime`、`focusHumanVerificationWindow`。

## 8. 优点（应保留）

- 后台临时标签页 + 会话复用，不打断用户浏览。
- 「接口优先 + 页面兜底 + 仅访问」三层能力齐全。
- 认证多来源兜底（缓存 / cookie / session / OAuth / localStorage token）健壮。
- 人机验证识别与「前置窗口交人工」的人机协作思路成熟。
- 纯函数工具模块 + `node --test`，逻辑可测试。

## 9. 缺口与痛点（本次重构要解决）

1. **场景硬编码**：`checkInSite` 用 `if (type===...)` 分流，三类站点各自一大段流程；「cookie 访问即签 / 需重新登录 / 需手动点击」无法作为站点级可配置项，只能靠代码分支硬凑。
2. **无「强制重新登录」策略**：只有在 401 / Cloudflare 报错后才被动清缓存重登，无法为「每次都需退出重登才发放」的站点主动配置。
3. **手动点击不可配置**：按钮全靠内置文案正则猜测；文案不匹配就失败，用户无法为某站点指定选择器或「打开页面交我手点」。
4. **单文件巨石**：`background.js` ~3600 行，认证/编排/DOM 注入/余额/验证混在一起，难维护、难加站点类型。
5. **无类型约束**：站点配置、结果、消息全是裸对象，字段靠约定，重构易错。
6. **注入脚本以字符串函数内联**：无类型检查、无复用、无独立测试，调试困难。
7. **站点类型封闭**：新增一类站点（新接口/新登录方式）要改多处，不具备插件式扩展点。

> 结论：能力足够，**架构不足**。重构重点不是重写签到逻辑，而是把已验证的能力**重新组织为可配置、可扩展、类型安全的策略模型**。下一篇 [02-方案设计.md](./02-方案设计.md) 给出这套模型。
