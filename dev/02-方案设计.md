# 02 · 方案设计

本篇给出重构版的**核心设计**：把「签到方式」抽象为可配置的站点策略，用统一模型收敛三类场景。

## 1. 三类场景的本质

用户提出的三个问题，本质是三种不同的「签到触发方式」：

| # | 场景 | 触发本质 | 现状能力 |
| --- | --- | --- | --- |
| A | 打开网站（cookie）即自动签到 | 仅需带 cookie 访问页面/接口，服务端自动记账 | 已有 `visit` 模式，但不读接口结果 |
| B | 需退出后重新登录才签到 | 必须重新走一次 OAuth / 登录换取新 session，再签 | 仅在报错后被动重登，无法主动配置 |
| C | 签到位置需手动点击 | 需要在页面特定元素上点击，或需人工过验证码 | 靠内置文案正则猜测，不可配置、易失败 |

三者不是「三种站点类型」，而是可以**自由组合**的两个正交维度：

- **认证维度（Auth Strategy）**：如何拿到「已登录」状态。
- **签到维度（Checkin Strategy）**：拿到登录态后如何触发签到。

现有实现把「站点类型（NewAPI/Sub2API/ZenAPI）」和「触发方式」耦合在一起。重构后把它们拆开。

## 2. 两个正交维度

### 2.1 认证策略 Auth Strategy

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| `cookie` | 直接复用浏览器对该域名已有的 cookie，不做任何登录动作 | 场景 A、已长期登录的站点 |
| `session-reuse` | 打开页面探测登录态（`/api/user/self` 等），有效则复用，无效才升级 | NewAPI 默认 |
| `oauth-linuxdo` | 走 linux.do OAuth 换取 token/session | NewAPI/Sub2API/ZenAPI 首次或过期 |
| `token-storage` | 从页面 localStorage/sessionStorage 读取指定 key 的 token | Sub2API/ZenAPI |
| `force-relogin` | **每次签到前强制重新登录**（清缓存 + 清 cookie/登出 + 重新 OAuth） | **场景 B** |

`force-relogin` 是本次**新增**能力：允许把「退出重登」从「报错后的补救」升级为「站点可主动声明的前置步骤」。

### 2.2 签到策略 Checkin Strategy

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| `api` | 用认证头向签到接口发请求，解析响应 | NewAPI/Sub2API/ZenAPI |
| `visit` | 仅带 cookie 打开页面（可刷新），读取余额，视为成功 | **场景 A** |
| `page-click` | 打开页面，按「选择器/文案」查找并点击签到按钮，捕获结果 | **场景 C**、接口兜底 |
| `manual-assist` | 打开页面并前置到前台，等待用户手点（人机验证/复杂交互），超时或用户确认后读结果 | **场景 C** 的人工兜底 |
| `record-only` | 仅记录站点条目，不参与签到：不开 tab、不走认证、不发请求；`executeAll` 会过滤，单站重试返回 `recorded` | 仅留档/统一查看 |

## 3. 站点档案 Site Profile（配置 Schema）

每个站点是一份声明式档案。用户只需配置，无需改代码。类型草案（TypeScript）：

```ts
type AuthStrategy =
  | 'cookie' | 'session-reuse' | 'oauth-linuxdo' | 'token-storage' | 'force-relogin';

type CheckinStrategy = 'api' | 'visit' | 'page-click' | 'manual-assist' | 'record-only';

interface SiteProfile {
  id: string;                    // 站点唯一 ID（域名派生）
  domain: string;                // cookie 域名
  name: string;                  // 展示名（可自动抓取）
  enabled: boolean;
  order: number;                 // 列表排序

  /** 站点预设：newapi / sub2api / zenapi / custom / record-only；仅用于填充默认值 */
  preset: 'newapi' | 'newapi-profile' | 'sub2api' | 'zenapi' | 'custom' | 'record-only';

  auth: {
    strategy: AuthStrategy;
    tokenKeys?: string[];        // token-storage：localStorage/session key 候选
    forceReloginEveryRun?: boolean; // 语义糖：等价 strategy=force-relogin
  };

  checkin: {
    strategy: CheckinStrategy;
    pageUrl: string;             // 签到页/访问页
    api?: {                      // strategy=api
      execUrl: string;
      method: 'GET' | 'POST';
      params?: Record<string, unknown>;
      queryUrl?: string;         // 二次核验
      successOnHttpOk?: boolean;
    };
    click?: {                    // strategy=page-click / manual-assist
      selectors?: string[];      // 用户可指定的按钮选择器（优先于内置文案）
      textPatterns?: string[];   // 追加文案（合并内置）
      keepTabForManual?: boolean;// 找不到/需人工时保留标签页到前台
      waitTimeoutMs?: number;
    };
  };

  humanVerification?: {
    focusWindowOnDetect?: boolean; // 命中验证码时前置窗口
  };

  balance?: { queryUrls?: string[]; pageSelectors?: string[] };
}
```

### 3.1 预设（Preset）如何映射到策略

用户添加站点时选 `preset` 或 `auto`，系统填充默认 `auth` + `checkin`，之后可逐项覆盖：

| Preset | 默认 auth | 默认 checkin | 关键默认值 |
| --- | --- | --- | --- |
| `newapi` | `session-reuse`（失败升级 `oauth-linuxdo`） | `api` | `execUrl=/api/user/checkin`, `queryUrl` 同 |
| `newapi-profile` | `bearer-sniff`（token 仅在内存，嗅探 Authorization） | `api`（标签页内执行带 cf_clearance） | `pageUrl=/profile`, `execUrl=/api/user/checkin` |
| `sub2api` | `token-storage`（key: `auth_token/access_token/token`），失败 `oauth-linuxdo` | `page-click`（页面优先，接口捕获） | `pageUrl=/check-in` |
| `zenapi` | `token-storage`（key: `user_token`），失败 `oauth-linuxdo` | `api`（标签页内执行） | `execUrl=/api/u/checkin`, `pageUrl=/user` |
| `custom` | `cookie` | `visit` | 全部由用户填 |
| `record-only` | `cookie`（占位，不实际使用） | `record-only` | 不派生接口配置；不参与自动签到 |

> 这样既保留参考实现里已验证的三套站点默认值，又允许「cookie 访问 / 强制重登 / 手动点击」按需覆盖。

## 4. 统一签到流水线

一条流水线服务所有站点，具体行为由 Profile 驱动：

```
loadProfile(site)
  → resolvePreset(填默认值)
  → AuthStep：按 auth.strategy 取得认证上下文 { headers?, tabId?, cookieOnly? }
       cookie          → 直接用现有 cookie，不登录
       session-reuse   → 探测登录态；无效则升级到 oauth
       token-storage   → 页面读取 token；无效则升级到 oauth
       oauth-linuxdo   → 走 OAuth（NewAPI/Sub2API/ZenAPI 各自入口）
       force-relogin   → 清缓存 + 清站点 cookie/登出 + 强制 oauth-linuxdo
  → CheckinStep：按 checkin.strategy 触发
       api          → 发请求 + 解析（401/403/CF 错误 → 触发 relogin 或 page-click 兜底）
       visit        → 打开页面（可刷新）+ 读余额 → 成功
       page-click   → 注入脚本，selectors 优先 → 文案兜底 → 捕获响应
       manual-assist→ 前置标签页交人工 → 轮询结果/超时
  → VerifyStep（可选）：queryUrl 二次核验
  → BalanceStep：响应 → 接口 → 页面文本
  → 记录结果，关闭/保留标签页
```

### 4.1 三类场景在流水线中的落点

- **场景 A（cookie 访问即签）**：`auth=cookie` + `checkin=visit`。不做任何登录动作，打开页面、读余额、记成功。若该站点其实需要读接口结果，可用 `auth=cookie` + `checkin=api`。
- **场景 B（退出重登）**：`auth=force-relogin` + `checkin=api|page-click`。每轮先清缓存、清该域名 cookie（相当于登出）、再走一次 OAuth，拿到全新 session 后再签。
- **场景 C（手动点击）**：
  - 能定位按钮：`checkin=page-click` + `click.selectors=['#sign-in-btn']`（用户指定，优先于内置文案）。
  - 需人工（验证码/复杂交互）：`checkin=manual-assist` + `click.keepTabForManual=true` + `humanVerification.focusWindowOnDetect=true`，扩展打开页面并切到前台，用户点完扩展读结果。

### 4.2 策略即插件（扩展点）

`AuthStep` 和 `CheckinStep` 各自是一个注册表：

```ts
authRegistry.register('force-relogin', forceReloginStrategy);
checkinRegistry.register('page-click', pageClickStrategy);
```

新增一类站点 = 新增/组合策略 + 一份 preset 默认值，**不改流水线主干**。这是对现有 `if (type===...)` 巨石的根治。

## 5. 结果模型（保留并细化）

```ts
type CheckinStatus = 'success' | 'already' | 'checking' | 'failed' | 'invalid' | 'needs-human';

interface CheckinResult {
  status: CheckinStatus;
  message: string;
  balance?: string;
  queryVerified?: boolean;
  strategyUsed?: { auth: AuthStrategy; checkin: CheckinStrategy }; // 便于诊断
  requiresManual?: boolean;   // 提示用户去前台标签页手动完成
}
```

新增 `needs-human` 状态，把「需人机验证/需手点」与普通 `failed` 区分，UI 可给出「去完成」入口而非单纯报错。

## 6. UI 变化要点

- 站点条目上的「模式」按钮从「访问/自动」二态，改为展示当前 `auth × checkin` 组合，点击进入**策略编辑**面板。
- 新增站点时：`preset` 下拉（NewAPI/NewAPI 个人资料/Sub2API/ZenAPI/自定义/仅记录）+ 「高级」折叠区（认证策略、签到策略、选择器、强制重登开关）。
- `needs-human` 结果显示「去完成」按钮，直接激活对应前台标签页。
- 其余（列表、拖拽排序、导入导出、每日定时、余额展示）沿用参考实现交互。

## 7. 兼容与迁移

- 导入旧版配置：`{domain,name,enabled,type,mode,pageUrl}` → 映射为 Profile（`type→preset`，`mode:visit→checkin:visit` 等），缺失字段用 preset 默认值补齐。
- 存储键保持可迁移：新版用 `siteProfiles`，首次启动时若检测到旧 `userSites` 则一次性迁移并保留备份。
