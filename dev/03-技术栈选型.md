# 03 · 技术栈选型

回答用户的核心问题：**是否用 TypeScript？是否用框架？用哪个？**

## 1. 结论先行

| 维度 | 推荐 | 备选 |
| --- | --- | --- |
| 语言 | **TypeScript** | 原生 JS（不推荐） |
| 扩展框架 | **WXT**（基于 Vite 的浏览器扩展框架） | Vite + CRXJS 插件 |
| UI 框架 | **无 / 轻量（原生 + 少量组件）** 或 **Svelte** | React（偏重） |
| 打包 | Vite（WXT 内置） | esbuild / rollup |
| 测试 | **Vitest** | node --test（现状） |
| 代码规范 | ESLint + Prettier + tsc | — |

**一句话**：用 **TypeScript + WXT** 重写。TS 解决现有「裸对象、无类型、易错」的问题；WXT 解决「MV3 样板、多入口打包、HMR、跨浏览器」的工程问题；UI 保持轻量，不引入重型前端框架。

## 2. 为什么要上 TypeScript

现有实现的痛点几乎都能被类型系统缓解：

- **配置/结果/消息全是裸对象**：`SiteProfile`、`CheckinResult`、消息 `action` 一旦用 union type + interface 约束，字段拼写、状态取值、消息分支都在编译期报错。
- **策略模型强依赖契约**：`AuthStrategy` / `CheckinStrategy` 用字面量联合类型 + 策略接口，注册表和实现自动对齐，新增策略时漏实现会被 tsc 拦下。
- **注入脚本参数**：`chrome.scripting.executeScript` 的 `func` + `args` 用泛型约束，避免「传参顺序错/字段名错」这类只能在运行时炸的问题。
- **重构安全**：3600 行巨石拆分为多模块时，类型是最好的护栏。
- **生态**：`@types/chrome` 提供完整的 MV3 API 类型。

> 代价：需要构建步骤（不能再「改完直接加载」）。但对本项目复杂度而言收益远大于成本，且 WXT 的 dev 模式有热重载，开发体验优于现状。

## 3. 为什么选 WXT 而不是「原生 + 手写构建」

**WXT**（`wxt.dev`）是目前浏览器扩展的主流框架，相当于「扩展界的 Nuxt」：

- **零样板 MV3**：约定式入口（`entrypoints/background.ts`、`entrypoints/popup/`、`entrypoints/*.content.ts`），自动生成 `manifest.json`。
- **开发体验**：基于 Vite，`wxt dev` 提供 HMR、自动重载扩展。
- **跨浏览器**：一套代码产出 Chrome / Firefox / Edge（`wxt build -b firefox`），`browser` 命名空间 polyfill 内置。
- **TypeScript 一等公民**，`storage`、`messaging` 等有类型化封装可选。
- **产物即标准扩展**：`wxt build` 输出可直接「加载已解压」或打包上架。

### 3.1 框架方案对比

| 方案 | 优点 | 缺点 | 适配本项目 |
| --- | --- | --- | --- |
| **WXT** | 约定式入口、自动 manifest、HMR、跨浏览器、TS 友好 | 需学习其约定；框架有一定「魔法」 | ⭐⭐⭐⭐⭐ 推荐 |
| **Vite + CRXJS** | 更接近裸 Vite，控制力强 | manifest 与入口需手写更多；CRXJS 维护活跃度需关注 | ⭐⭐⭐⭐ 备选 |
| **Plasmo** | 功能全、组件化强 | 偏重、约定多、更适合 React 重 UI 场景 | ⭐⭐⭐ |
| **原生 JS + 手写 rollup/esbuild** | 无框架依赖 | MV3 样板、多入口、HMR 全部自己搞；等于重复造轮子 | ⭐⭐ |
| **保持现状（原生无构建）** | 零构建、改完即用 | 无类型、巨石难维护、无法支撑策略化重构 | ⭐ 不推荐 |

## 4. UI 框架：建议保持轻量

popup 是一个 ~400px 宽的列表 + 表单，交互不复杂。参考实现用原生 DOM 已经够用。

- **首选**：原生 TS + 少量组件封装（列表、对话框、策略编辑面板）。零运行时开销，popup 秒开。
- **可选**：**Svelte**（编译期框架、产物极小、写起来比原生舒服）。若策略编辑面板变复杂，Svelte 是性价比最高的升级。
- **不建议**：React（运行时较重，对这个体量的 popup 收益不明显）。

> 建议 MVP 阶段用原生 TS，若 UI 复杂度上升再引入 Svelte（WXT 对 Svelte/Vue/React 均有模板支持，切换成本低）。

## 5. service worker（MV3）注意事项

- background 是**非持久 service worker**，随时可能被回收。所有状态必须落 `chrome.storage`，不能只放内存变量（现有 `automationHumanVerificationMonitors` 这类内存态需评估：worker 重启后监控会丢失，重构时应尽量减少对内存态的强依赖，或用 `alarms` + storage 恢复）。
- `setInterval`/`setTimeout` 在 worker 里不可靠，长轮询应改用 `chrome.alarms` 或短生命周期任务。
- 注入页面的脚本（content-side）与 background 通过 `chrome.runtime.sendMessage` / `scripting.executeScript` 通信，建议用类型化消息层。

## 6. 测试与质量

- **Vitest** 替代 `node --test`：与 Vite/WXT 同生态，支持 TS、mock `chrome.*`（配合 `@webext-core/fake-browser` 或手写 mock）。
- 纯逻辑（策略选择、响应解析、URL 推导、余额提取、Profile 迁移）保持纯函数，单测覆盖。
- DOM 注入脚本抽成独立可测函数（传入 `document` / 配置，返回结构化结果），比现状「内联字符串函数」可测性大幅提升。
- CI：`tsc --noEmit` + `eslint` + `vitest run` + `wxt build`。

## 7. 依赖清单（预期）

| 依赖 | 用途 |
| --- | --- |
| `wxt` | 扩展框架（含 Vite） |
| `typescript`、`@types/chrome` | 语言与 API 类型 |
| `vitest` | 测试 |
| `eslint`、`prettier` | 规范 |
| `svelte`（可选） | UI（如需） |
| `zod`（可选） | Profile / 导入配置的运行期校验，与 TS 类型互补 |

> `zod` 对「导入用户 JSON 配置」很有用：既能运行期校验，又能 `z.infer` 出 TS 类型，避免类型与校验两套维护。

## 8. 取舍说明

- 选 TS + 构建，牺牲「改完即用」，换来可维护性与重构安全，**对策略化重构是必要前提**。
- 选 WXT 而非裸 Vite，牺牲少量「框架魔法」的透明度，换来 MV3 样板与跨浏览器的省心。
- UI 暂不上重框架，避免 popup 体积与启动开销。

如果团队更偏好完全掌控、不想引入框架「约定」，**Vite + CRXJS + TypeScript** 是等价可接受的备选，其余设计（策略模型、目录结构）完全不受影响。
