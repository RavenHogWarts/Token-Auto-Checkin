# 公益站自动签到助手 · 使用文档

面向使用者的操作说明。开发/设计文档见 [`dev/`](../dev)，构建说明见 [`README.md`](./READ../README.md

> 数据只保存在本地浏览器（`chrome.storage.local`），不上传任何服务器。

---

## 一、安装

### 方式 A：加载构建产物（推荐给使用者）

1. 执行 `pnpm install && pnpm build`，产物在 `.output/chrome-mv3`。
2. 打开 `chrome://extensions/`，右上角开启「开发者模式」。
3. 点「加载已解压的扩展程序」，选择 `.output/chrome-mv3` 目录。
4. 建议点击工具栏拼图图标，把「公益站自动签到助手」固定，方便随时打开。

### 方式 B：开发模式（改代码时用）

```bash
pnpm dev
```

WXT 会自动打开一个带扩展的浏览器并热重载。

## 二、界面速览

弹窗顶部有两个标签页：**站点**（默认）与**运行日志**。「站点」标签从上到下：

| 区域                | 说明                                                     |
| ------------------- | -------------------------------------------------------- |
| 顶部标题            | 显示每日自动签到时间                                     |
| 统计行              | 站点总数 / 成功 / 已签 / 失败 数量                       |
| **立即签到** 按钮   | 手动触发全部启用站点签到；运行中变为「签到中，点击终止」 |
| 站点列表            | 每个站点一行：开关、类型标签、名称、余额、状态、更多菜单 |
| + 添加站点          | 打开站点编辑器（含可折叠的「高级设置」）                 |
| 人机窗口前置        | 开关：遇到人机验证时把验证页面切到前台交你处理           |
| 导出配置 / 导入配置 | 备份与恢复（JSON）                                       |
| 每日签到            | 设置每天自动签到时间并保存                               |

站点行上的元素：

- **开关**：启用/禁用该站点（禁用的站点不参与签到）。
- **类型标签**：显示预设（NewAPI / Sub2API / ZenAPI）或「仅访问」。
- **名称**：点击后台打开该站点签到页。
- **状态**：见「状态含义」一节；失败/失效可点击重试。

## 三、添加站点

1. 点「+ 添加站点」，打开站点编辑器。
2. 填**签到页地址**，例如 `c.com/console/personal` 或 `https://c.com/console/personal`（也可只填域名 `c.com`）；站点名称可留空（默认用域名）。
3. 选**站点预设**（切换预设会自动回填对应的默认接口与策略）：
   - **NewAPI**：常见 `/api/user/checkin`，优先复用登录态，必要时走 OAuth。
   - **NewAPI 个人资料签到**：签到入口在 `/profile`、走原生签到接口，认证用 `bearer-sniff`
     （嗅探页面自身请求的认证头，兼容 access token 仅在内存的新版 New API）。见第四节。
   - **Sub2API**：`/check-in` 页面，读取本地 token，页面点击签到。
   - **ZenAPI**：`/user` 页面，`/api/u/checkin` 接口，标签页内执行。
   - **自定义**：只打开页面（靠 cookie 自动签到），读取余额即视为成功。
4. 如需自定义认证/签到策略、OAuth 登录方、按钮选择器等，展开「▸ 高级设置」（见第四节）。
5. 点「保存」。

> 编辑已有站点：站点行「⋯」→「编辑」，打开的是同一个编辑器（高级设置默认展开）。

## 四、三类签到场景怎么配

本工具把「怎么签到」拆成两个可组合的维度：**认证策略**（怎么拿到登录态）× **签到策略**（怎么触发签到）。常见三类场景对应关系：

| 你的情况                         | 认证策略        | 签到策略                                                             | 怎么配                                       |
| -------------------------------- | --------------- | -------------------------------------------------------------------- | -------------------------------------------- |
| **打开网站（cookie）就自动签到** | `cookie`        | `visit`                                                              | 添加时选「自定义」预设即可                   |
| **需要退出后重新登录才发放**     | `force-relogin` | `api` 或 `page-click`                                                | 高级设置里认证策略选 `force-relogin`         |
| **个人资料页签到（新版 NewAPI，token 只在内存）** | `bearer-sniff` | `api`                                             | 添加时选「NewAPI 个人资料签到」预设即可      |
| **签到位置需要手动点击**         | 视站点而定      | `page-click`（可自定义按钮选择器）或 `manual-assist`（前台交你手点） | 高级设置里签到策略选 `page-click`，填选择器  |

**「重新登录」不一定走 linux.do，也可能是 GitHub。** 在高级设置的「OAuth 登录方」里选择 `linuxdo` 或 `github`，扩展会点击站点登录页上对应的第三方登录入口。

**添加或编辑站点时**，展开「▸ 高级设置」即可直接配置：认证策略、OAuth 登录方、Token 键名、签到策略、签到接口 URL/方法/核验接口、按钮选择器与文案、找不到按钮时前台交人工、人机验证前置——表单按所选策略自动显示相关字段。也可通过**导出→编辑 JSON→导入**批量配置（见第七节）。

### 认证策略一览

| 值              | 含义                                                              |
| --------------- | ----------------------------------------------------------------- |
| `cookie`        | 直接用浏览器已有 cookie，不做登录动作                             |
| `session-reuse` | 探测登录态，有效就复用，失效才升级到 OAuth                        |
| `token-storage` | 从页面 localStorage/sessionStorage 读取 token（可配 `tokenKeys`） |
| `bearer-sniff`  | 用 webRequest 嗅探页面自身 `/api/*` 请求的认证头（`Authorization: Bearer` 或 `New-Api-User`），兼容 token 只在内存的新版 New API；捕获后在标签页内执行签到 |
| `oauth-linuxdo` | 走 OAuth 登录（提供方见「OAuth 登录方」）                        |
| `force-relogin` | **每次签到前彻底登出**（调官方登出接口 + 清 localStorage/sessionStorage 登录态 + 清该站点 cookie）再重新 OAuth |

> **OAuth 登录方**：`linuxdo`（默认）或 `github`。决定 OAuth / 重新登录时点击站点登录页上的哪个第三方登录按钮。

### 签到策略一览

| 值           | 含义                                      |
| ------------ | ----------------------------------------- |
| `api`        | 调用签到接口                              |
| `visit`      | 仅打开页面（带 cookie），读余额即视为成功 |
| `page-click` | 打开页面，按选择器/文案找到签到按钮并点击 |

### 签到位置需要先导航（导航点击 / navSteps）

有些站点**无法直接打开签到页**——例如 `page-click` 策略下，页面加载后会被前端重定向走，签到按钮藏在「头像 → 个人资料」里。此时用「高级设置 → 导航点击」：填写到达签到位置前**依次点击**的目标，每行一个，**先当 CSS 选择器，匹配不到再当可见文案**。扩展会先按顺序点击导航，再查找签到按钮。

**示例：tabitoken / gorouter 等新版 NewAPI（签到在个人资料页，token 只在内存）**

推荐直接选预设 **「NewAPI 个人资料签到」**，无需配任何选择器：

- 站点预设：`NewAPI 个人资料签到`（自动填：签到页 `/profile`、认证 `bearer-sniff`、签到 `api`）
- 原理：打开 `/profile` → 嗅探页面自身请求的认证头（新版 `Authorization: Bearer` 或旧版 `New-Api-User`）
  → 在标签页内调 `POST /api/user/checkin`。**不依赖按钮选择器，页面改版也不受影响**。

> 仅当站点**没有可用签到接口**、只能点页面按钮时，才退回下面的 `page-click` + 导航点击方案。
> 不建议用 `#xxx` / `nth-of-type` 这类脆弱选择器——优先用文案匹配。

**（兜底）签到位置需要先导航再点击（`page-click` + navSteps）**

- 签到页地址：`https://<domain>/dashboard/overview`
- 签到策略：`page-click`
- 导航点击（每行一个，先当选择器、匹配不到再当可见文案）：
  ```
  .avatar
  个人资料
  ```
  先点头像，再按文案点「个人资料」进入 `/profile`，随后扩展在个人资料页找到并点击签到按钮。

> 小技巧：在目标页按 F12 → 右键元素「Copy → Copy selector」可获得选择器。

## 五、签到操作

- **手动全量签到**：点「立即签到」，会依次处理所有**启用**站点，状态实时更新。运行中按钮变为「签到中，点击终止」，可中途终止。
- **单站重试**：某站点状态为失败/失效时，点它的状态标签即可只重试该站点。
- **每日自动签到**：默认每天 09:00。在「每日签到」处改时间并点「保存」。首次安装或浏览器启动时会自动登记定时。

> 自动签到依赖浏览器在设定时间处于运行状态；若到点时浏览器未开，Chrome 会在下次唤醒时补触发。

## 六、运行日志

切到顶部「运行日志」标签，可查看每次签到的过程记录：批量/单站开始、每个站点的结果（成功 / 已签 / 失败 / 失效 / 待人工，含余额）、本轮汇总。

- 最多保留最近 200 条，新的在最上方；签到时实时刷新。
- 点「清空」可清除全部日志。
- 排查某站点为何失败时，先看这里的结果消息（如「未找到签到按钮，页面候选: …」）再决定补选择器还是改用人工。

## 七、导出 / 导入配置（含高级策略）

### 导出

点「导出配置」，下载一个 JSON 文件，结构为：

```json
{
  "version": 2,
  "profiles": [ /* SiteProfile 数组 */ ],
  "autoSignTime": "09:00",
  "focusHumanVerificationWindow": false
}
```

### 导入

点「导入配置」选择 JSON。若当前已有站点，会让你选择**覆盖**或**合并**。校验规则：每个 profile 必须有 `domain` 和 `checkin.pageUrl`。

### 站点档案（SiteProfile）字段

```jsonc
{
  "id": "c_com",                 // 域名点转下划线，唯一
  "domain": "c.com",
  "name": "示例站",
  "enabled": true,
  "order": 0,
  "preset": "newapi",            // newapi | newapi-profile | sub2api | zenapi | custom
  "auth": {
    "strategy": "session-reuse", // 见认证策略一览
    "oauthProvider": "linuxdo",  // linuxdo | github，OAuth / 重新登录用
    "tokenKeys": ["user_token"], // 仅 token-storage 用
    "forceReloginEveryRun": true // 语义糖：等价 strategy = force-relogin
  },
  "checkin": {
    "strategy": "api",           // 见签到策略一览
    "pageUrl": "https://c.com/console/personal",
    "api": {
      "execUrl": "https://c.com/api/user/checkin",
      "method": "POST",
      "queryUrl": "https://c.com/api/user/checkin",
      "successOnHttpOk": false
    },
    "click": {
      "selectors": ["#sign-in-btn", ".checkin button"], // 自定义按钮，优先于内置文案
      "textPatterns": ["立即签到"],
      "navSteps": [".avatar", "个人资料"], // 到达签到位置前依次点击（先选择器后文案）
      "keepTabForManual": false,
      "waitTimeoutMs": 20000
    }
  },
  "humanVerification": { "focusWindowOnDetect": true },
  "balance": { "queryUrls": [], "pageSelectors": [] }
}
```

### 三类场景的配置示例

**场景 A · 打开网站即签（cookie）** —— 等价于添加时选「自定义」：

```json
{
  "id": "a_com", "domain": "a.com", "name": "A 站", "enabled": true, "order": 0,
  "preset": "custom",
  "auth": { "strategy": "cookie" },
  "checkin": { "strategy": "visit", "pageUrl": "https://a.com/" }
}
```

**场景 B · 需退出重新登录**：

```json
{
  "id": "b_com", "domain": "b.com", "name": "B 站", "enabled": true, "order": 1,
  "preset": "newapi",
  "auth": { "strategy": "force-relogin" },
  "checkin": {
    "strategy": "api", "pageUrl": "https://b.com/console/personal",
    "api": { "execUrl": "https://b.com/api/user/checkin", "method": "POST" }
  }
}
```

**场景 C · 需手动点击（自定义选择器）**：

```json
{
  "id": "c_com", "domain": "c.com", "name": "C 站", "enabled": true, "order": 2,
  "preset": "custom",
  "auth": { "strategy": "cookie" },
  "checkin": {
    "strategy": "page-click", "pageUrl": "https://c.com/dashboard",
    "click": { "selectors": ["#daily-checkin"], "keepTabForManual": true }
  }
}
```

> 场景 C 若站点带验证码或交互复杂，把 `checkin.strategy` 改为 `manual-assist`：扩展会把页面切到前台，你手动点完即读取结果。

## 八、状态含义

| 状态       | 说明                     | 可点击重试     |
| ---------- | ------------------------ | -------------- |
| 待签       | 尚未签到                 | 是             |
| 签到中     | 正在处理                 | 否             |
| 成功       | 本次签到成功             | 否             |
| 已签       | 今日已签过               | 否             |
| 失败       | 签到失败（可点状态重试） | 是             |
| 失效       | 页面 404/410 或打不开    | 是             |
| **待人工** | 需完成人机验证或手动点击 | 显示「去完成」 |

**待人工（needs-human）**：扩展会保留该站点的标签页。点状态旁的「去完成」可直接切到该标签页，你完成人机验证/点击后，再对该站点单站重试即可。开启顶部「人机窗口前置」开关后，检测到验证时会自动把窗口切到前台。

## 九、余额显示

余额是**可选**信息，只展示**本轮**从签到响应、账户接口或页面文字中识别到的值；本轮没取到就不显示（不会显示历史旧值）。

## 十、常见问题

**Q：为什么会弹出 linux.do 授权页？**
A：只有在缓存与浏览器已有登录态都不可用时才会走 OAuth。请确保已在浏览器登录 linux.do。已登录且可复用的站点不会每次弹。

**Q：`force-relogin` 会影响我在该站点其他标签页的登录吗？**
A：会。该策略会清除目标域名的 cookie（等于登出）再重新登录，仅对配置了该策略的站点生效。只在「必须重登才发放」的站点使用。

**Q：自动没点到签到按钮怎么办？**
A：在该站点配置里给 `checkin.click.selectors` 填页面上签到按钮的 CSS 选择器（优先于内置文案匹配），或改用 `manual-assist` 手动完成。

**Q：接口签到失败会怎样？**
A：会自动尝试「重新登录后重试」和「打开官方页面点击签到」兜底；仍不行才记为失败。

**Q：数据会上传吗？**
A：不会。站点配置、结果、认证缓存都只存本地 `chrome.storage.local`。认证缓存 7 天过期，失效会自动重新获取。

## 十一、权限说明

| 权限               | 用途                                           |
| ------------------ | ---------------------------------------------- |
| `cookies`          | 读取/清除站点与 linux.do 登录态                |
| `storage`          | 保存配置、结果、认证缓存                       |
| `alarms`           | 每日定时签到                                   |
| `tabs` / `windows` | 后台打开临时页面、前置人机验证窗口             |
| `scripting`        | 在页面读取登录态、点击签到按钮、读余额         |
| `webRequest`       | 嗅探页面自身请求的认证头（`bearer-sniff` 策略，兼容 token 只在内存的新版 New API） |
